## 結論

「記録を蓄積し、複数試合の分析価値で収益化する」という長期方針は維持する。
ただし、長期メモリの完成を課金開始の前提にしない。

推奨順序:

1. 既存処理を含むAI呼び出し基盤の改善。
2. 月間レポート＋根拠付き練習提案を提供。
3. 利用状況とフィードバックを確認。
4. 有料プランの小規模提供を判断。
5. 必要性を確認してから長期メモリを追加。

## 旧プランからの変更

| 項目 | 新しい方針 |
| --- | --- |
| AIクライアント | 新機能専用にせず、既存の試合アドバイスにも適用する |
| 失敗文言の保存 | スコープ外にせず、最初のSprintで解消する |
| 長期メモリ | レポートより後に回し、当面は実装しない |
| 月間レポート | 長期メモリに依存せず、保存された試合データを集計して生成する |
| 凡ミス | 月間レポートの分析対象に追加する |
| 再生成条件 | 新規追加だけでなく、編集・削除・日付変更・完了への変更も扱う |
| コスト管理 | キャッシュに加え、サーバー側の同時生成防止と使用量計測を行う |
| 課金開始 | 長期メモリ完成ではなく、利用価値・支払い需要・原価を判断材料にする |

維持する方針は、オンデマンド生成、結果保存、集計値を中心としたAI入力、レポートと練習提案の一括生成。
worker dynoやSchedulerの導入は今回の前提にしない。

## 全Sprintで守る分析の原則

- 技術の得点構成比を、成功率や技術の使用頻度と混同しない。
- 構成比が増えただけで「上達した」と断定しない。
- 得点、相手の好プレー、自分の凡ミスを区別する。
- 凡ミス記録導入前のゼロを「ミスがなかった」と解釈しない。記録の有無を判別できない場合は比較の限界を示す。
- 技術分析とサーブ・レシーブ分析は別の記録方式として扱い、分母や対象を混ぜない。
- 各指標について、対象試合数・対象ポイント数・対象期間を明示する。
- 勝敗不明、戦型未設定、比較対象月なし、データ不足をゼロや敗北に置き換えない。
- 少数データや対戦相手の違いによる変動を、改善・悪化の証拠として断定しない。
- 凡ミスの原因や、記録にない相手の技術を推測で創作しない。
- AIが提案した練習と、本人が実際に取り組んだ練習を区別する。
- レポートの結論と練習提案は、表示された集計値を根拠として説明できるようにする。

## Sprint 1: 既存AIを含む基盤の改善

目的: 現在の試合アドバイスを安定して提供し、新機能の原価と失敗を把握できる状態にする。

推奨ブランチ: `feature/sprint-1-ai-foundation`

### 範囲

- 既存の技術分析・サーブレシーブ分析の双方で、共通のAI呼び出し基盤を使用する。
- 成功と失敗を明確に区別し、エラー文言や空の応答を有効なアドバイスとして保存しない。
- 失敗時も試合データと基本分析を表示し、利用者が明示的に再試行できるようにする。
- 既に保存された既知の失敗文言についても、再試行できる扱いを計画する。正常な回答を一括削除しない。
- 接続・読み込み等のタイムアウトと、リクエスト全体の時間予算を設計する。
- 同一リクエスト内で長期メモリ更新を追加しない。自動リトライによる時間・費用増加にも注意する。
- プロンプト、回答本文、APIキーなどをログに出さない。
- 機能種別、モデル、成功・失敗、処理時間、取得可能なトークン使用量を記録する。
- モデルやAPIパラメータの互換性は着手時に公式仕様を確認する。モデル変更自体は目的にしない。
- 同時アクセスや連打で、同一対象のAI生成が重複しないようにする。

Herokuの通常のリクエストには30秒の制約がある。個々の読み込みタイムアウトを設定するだけで、全体の上限を保証したとみなさない。
参考: https://help.heroku.com/FSLHW32O/why-am-i-getting-h12-request-timeout-errors-in-ruby

### 完了条件

- 既存の両分析フローで正常なアドバイスを表示・再利用できる。
- APIエラー、タイムアウト、不正・空応答を保存しない。
- 失敗後に再試行でき、保存済みの既知の失敗文言にも回復経路がある。
- 他ユーザーのデータにはアクセスできない。
- 本文や秘密情報がログに出ない。
- 時間予算と同時生成防止の検証結果を報告できる。
- 使用量取得不能の場合も、ゼロ使用と誤認する記録にならない。

## Sprint 2: 月間レポート＋根拠付き練習提案

目的: 単発の試合アドバイスを超える振り返りの価値を、小さな範囲で提供する。

推奨ブランチ: `feature/sprint-2-monthly-report`

### 利用者の流れ

1. 月間レポート一覧から対象月を選ぶ。
2. 対象試合数と生成条件を確認して生成する。
3. 要約、良かった点、課題、次の練習提案を読む。
4. 生成済みの内容は、再度AIを呼ばずに閲覧する。
5. 対象データが変わった場合、更新が必要と分かり、再生成できる。

### 内容と生成条件

- 完了試合を対象に、試合日基準で月を選ぶ。
- 試合数、勝敗、比較可能な前月との差、技術の得点構成比、凡ミスの傾向、戦型別傾向、サーブ・レシーブ傾向を扱う。
- データがない分析項目は無理に埋めず、対象なし・不足を示す。
- 当面は2試合以上を生成条件の案とする。ただし分析可能なデータを伴う試合の数え方を計画時に明確にする。
- 2試合あれば信頼できる傾向が確定する、とは扱わない。
- 前月のデータがなくても当月の振り返りは提供できる。
- 当月は途中経過として表示し、未来月は生成できない。
- 練習提案は1〜3件を基本とし、内容、根拠、目安時間を示す。
- レポートと練習提案を同じAI呼び出しで生成する。
- 長期メモリは使わず、対象期間の保存データを集計して入力する。
- JSON等の形式だけでなく、必要項目・型・件数・値の妥当性を検証してから保存する。

### 更新・原価・失敗時の扱い

- 新規試合の追加、既存データの編集・削除、試合日の月移動、下書きの完了を再生成判定に反映する。
- 前月比較を含む場合は、比較対象データの変更も考慮する。
- 親レコードの更新日時だけで、すべての関連データ変更を検知できると仮定しない。
- 生成中にデータが変わった場合、古い入力の結果を最新と表示しない。
- 削除された試合に基づく古いレポートを、そのまま最新の有効な結果として表示しない。
- 対象データが変わっていない場合は保存済み結果を利用する。
- 生成ボタンの連打防止に加えて、サーバー側でも同時生成を防ぐ。
- 過剰な再生成を防ぐ回数制限・待機時間は、着手計画で具体化する。無制限生成を前提にしない。
- 再生成が失敗しても有効な保存済み結果を破壊しない。古い内容を表示する場合は対象時点を明示する。
- ナビゲーションはPCとモバイルの双方に用意する。

### 完了条件

- 通常生成、保存済み閲覧、変更後の再生成、生成失敗後の再試行ができる。
- 未ログイン、不正な月、未来月、他ユーザーのレポートへのアクセスを適切に処理する。
- 少数データ、前月なし、凡ミス記録の有無が不明、分析方式の混在を正しく扱う。
- 削除・編集・月移動・下書き完了・同時生成をテストする。
- 練習提案の根拠と画面上の数値が矛盾しない。

## Sprint 3: 利用計測と軽いフィードバック

目的: レポートが練習と継続記録につながるかを確認する。

推奨ブランチ: `feature/sprint-3-report-feedback`

### 範囲

- レポートへの「役立った／役立たなかった」などの軽い評価を提供する。
- 練習提案から「取り組む課題」を選べる最小限の導線を検討する。
- 課題を選んだことを、実際に練習した証拠として扱わない。
- 初回試合登録、2試合目への到達、翌月の記録継続を確認できるようにする。
- レポート生成成功、閲覧・再閲覧、フィードバックを計測する。
- レポート本文、選手名、メールアドレス等を外部解析イベントへ送信しない。
- 成功・失敗・再生成を含むAI利用量を、原価評価に使える形で集計する。
- 必要な最小限の集計に留め、専用の大規模な管理画面は今回作らない。

### 完了条件

- 各指標の対象者・期間・分母が定義されている。
- 再読み込み等でイベントが意図せず重複計上されない。
- フィードバックが保存され、本人以外は変更できない。
- 技術分析とサーブ・レシーブ分析への既存導線を損なわない。
- 実データによる評価の期間・件数と、未検証事項を報告できる。

## 課金への進み方: 別途判断する段階

以下は方針案であり、この文書だけでStripe導入や既存機能の有料化を開始しない。

| 枠 | 候補 |
| --- | --- |
| 無料 | 試合記録、記録閲覧、基本集計、回数を限定したAI体験 |
| 有料 | 複数試合の振り返り、期間比較、根拠付き練習提案、将来の継続コーチング |

- 既存無料機能を広く制限する前に、新しい継続価値への支払い需要を確かめる。
- 生の試合記録や基本的な振り返りの導線は維持する方向で検討する。
- 閲覧制限だけではAI原価を制御できないため、生成回数も設計する。
- 初月無料トライアルは固定しない。無料レポート1回なども比較する。
- 価格、無料回数、既存利用者への扱い、課金・解約・失敗時の挙動は別途計画する。
- 月間レポートを使えるだけの試合数を記録している利用者がどれだけいるか確認する。
- 利用継続や好意的な評価を支払い需要と同一視しない。小規模な有料提供で実際の購入・継続を確認する。
- 判定の数値基準は実際の母数を見て設定する。根拠のない固定閾値を本書では置かない。

## 長期メモリを再検討する際の条件

導入目的は「記憶機能があること」ではなく、過去の課題と次の助言を有益につなぐこと。
利用者がその継続性を求めていることを確認してから設計する。

旧プランの「現在の要約＋今回のアドバイスを400字へ要約」だけでは、以下が不足する。

- 試合日と閲覧順が異なる場合の時系列整合性。
- 試合の編集・削除後の再構築。
- 同時更新による上書き消失の防止。
- アドバイス生成成功後にメモリ更新だけ失敗した場合の再試行。
- AI提案と実際の練習行動の区別。
- 根拠となる試合、対象期間、要約の更新条件の追跡。
- リセット時の既存試合の再反映方針。

閲覧・リセットUIはメモリ機能と同じSprintで提供する。
過去月のレポートに、後の時期の記憶を混ぜない。
試合詳細の表示にAI呼び出しを直列追加する設計を前提にしない。

## 実装・検証・引き継ぎのルール

1. 着手時に最新の指示、ブランチ、作業ツリー、関連コード、既存テストを確認する。
2. plannerで対象Sprintの計画を具体化し、プロジェクト規約に沿ってユーザー承認を受ける。
3. generatorは新規ブランチで1 Sprintだけ実装する。
4. 修正点が出た場合も、修正計画を立ててから対応する。
5. 実装後はRSpecとRuboCopの両方を実行し、すべてパスしたことを確認する。
6. evaluatorは実際のブラウザで対象フローを操作して合否を報告する。
7. ログイン検証には使い捨ての新規テストユーザーを使う。既存ユーザーのパスワードやデータは変更しない。
8. API障害の検証はスタブ等の隔離された方法で行う。共有環境や本番のAPIキーを不正値に変更しない。
9. PRはユーザーから明示的に指示された後に、既存テンプレートを使って作成する。
10. plansファイルは対象の実装コミットと一緒にコミットする。無関係な作業を混ぜない。
11. 次Sprintへ進むには、前SprintのPRマージとユーザーの明示的な指示の両方が必要。
12. migrationを含む場合は、本番への適用順序・適用確認を計画し、新コードが未適用スキーマに依存する期間を避ける。

必須チェック:

```bash
bundle exec rspec && bundle exec rubocop --parallel
curl -s -o /dev/null -w "%{http_code}" http://localhost:3000
```

アプリ起動確認は200が条件。未実施の検証を合格と報告しない。
